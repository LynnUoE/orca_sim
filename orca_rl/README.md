# orca_rl — PPO baseline for OrcaHand in-hand reorientation

放到 `orca_sim/` 仓库根目录下（和 `src/`、`random_policy.py` 平级），就能直接跑。

```
orca_sim/
├── src/orca_sim/        # 原仓库
├── random_policy.py
└── orca_rl/             # 这个包
    ├── task.py          # 修好的任务：奖励 + 成功判据 + 动作空间
    ├── checks.py        # 证明奖励漏洞已修复
    ├── train.py         # PPO 训练
    ├── evaluate.py      # 诚实的评估
    └── record.py        # 录视频
```

## 训练

```bash
python -m orca_rl.train --name run1 --timesteps 20_000_000 --n-envs 8
```

**接着已有模型练下去**（不要浪费已经跑出来的策略）：

```bash
python -m orca_rl.train --name run3 --resume runs/run2/final_model.zip \
       --timesteps 20_000_000 --n-envs 8
```

`--resume` 会一并载入同目录的 `vecnormalize.pkl`。**这一点很重要** —— 观测归一化的统计量如果从零重新累积，等于给策略喂了尺度不同的观测，表现会像是「突然失忆」。步数计数也接着走，TensorBoard 上是连续的一条线。

超参数按命令行重新读取，所以 `--resume` 的同时改 `--lr` 之类是生效的。注意课程难度存在环境里、不随模型保存，续训会从 `--curriculum-start-deg`（默认 30°）重新开始。

`--n-envs` 设成你 Mac 的性能核心数。M1/M2 Pro 一般是 8，M3 Max 可以到 12。开太多反而会因为调度开销变慢，先跑几分钟看 `fps` 再定。

产物全在 `runs/run1/`：`final_model.zip`、`vecnormalize.pkl`（评估时必须要）、`checkpoints/`、`tb/`。

```bash
tensorboard --logdir runs/
```

**要看的不是 `ep_rew_mean`，是 `task/` 那一组：**

| 指标 | 含义 | 期望 |
|---|---|---|
| `task/drop_rate` | 掉落率 | 最先下降。几十万步内应该从 ~90% 掉到 20% 以下 |
| `task/solves_per_episode` | 每 episode 完成几次翻转 | **真正的进度指标。**长时间是 0 就是没学会 |
| `task/solved_any_frac` | 至少完成一次的 episode 占比 | 从 0 开始爬升 |
| `train/clip_fraction` | 更新幅度 | 健康值 0.05–0.2 |
| `train/approx_kl` | 策略移动距离 | 应该被 `target_kl=0.02` 压住 |
| `train/std` | 动作标准差 | 应在 0.6 附近缓慢下降。**涨上去说明熵失控**，掉到接近 0 说明探索死了 |
| `task/goal_angle_deg` | 当前课程难度 | 从 30° 起步，应该缓慢上升 |

学习通常分两个阶段：**先学会不掉方块**（drop_rate 快速下降，但 solves 还是 0），**然后才学会转**（solves 开始爬）。第一阶段一般几十万步，第二阶段慢得多。如果 500 万步后 solves 还是 0，别干等，去调参或者看视频。

## 改了什么

### 1. 奖励不再奖励「不完成任务」

原来：每步 `0.5 * (alignment + 1)`，成功即终止。悬停在阈值外 200 步 ≈ 196 分，20 步真解 ≈ 10 分 —— PPO 必然学会悬停。

现在：

```
r = shaping_coef * Δalignment          # 势函数式，只有「进步」得分，等待得 0
  + success_bonus     (完成时 +10)
  - drop_penalty      (掉落时 -5)
  - action_rate_penalty * ||Δtarget||²  # 动作平滑，对真机很重要
```

**成功不再终止 episode** —— 完成后奖励 +10 并换一个新目标，继续赚。做任务严格优于不做任务。

`Δalignment` 只在方块被握住时才计入，否则半空翻滚也能白拿 shaping 分。

### 2. 成功判据要求真的握住

必须同时满足：与手有接触（查 MuJoCo contact）、高于 `in_hand_height=0.15`、连续 `hold_steps=10` 步对齐。

`drop_height` 从 0.05 提到 0.10 —— 原来的 0.05 太低，方块早就离开手掌了才算掉。

### 3. 目标从简单的开始，按能力自动加难度

默认 `goal_mode="curriculum"`：目标是从当前朝向绕随机垂直轴转 θ 度，θ 从 30° 起步，上限 180°。

课程的升降级判据有两个关键设计（都是踩坑踩出来的，见文末复盘二）：

- **按速率不按次数** —— `successes × (400 / 实际步数)`。用绝对次数的话，一个 90 步就掉落的 episode 物理上装不下两次成功，会被误判成「太难」，于是掉落率一高课程就被系统性往下拽。
- **20 个 episode 的滑动窗口** —— 这个任务的 solves 方差极大（均值 0.84、最高 4、近一半是 0）。逐 episode 反应会让难度做随机游走，来回抵消。窗口平均 ≥1.0 升 5°、≤0.25 降 5°，调整后清空窗口在新难度上重新测量。

`task/goal_angle_deg` 和 `task/curriculum_solve_rate` 都会记进 TensorBoard。用 `--goal-mode axis` 可以切回固定的 6 个轴向目标，此时新目标必须与当前朝向相差至少 60°。不加这一条的话，6 个轴向目标里约 1/6 在 reset 时就已经满足，而且刚完成一次后重采样很容易抽到刚解完的那个 —— 白送成功。**这个 bug 我在实测中抓到过**：修之前随机策略每 40 个 episode 有 5 个拿到成功，修之后降到 1 个。

### 4. 动作空间统一成 `[-1, 1]^17`

原来是 17 个不同范围的关节角（有的跨度 1.05，有的 2.18，而且不对称），不归一化基本训不动。现在环境内部负责映射，**不需要 `RescaleAction` 包装器**。

默认 `action_mode="relative"`：动作是在上一个目标上的增量（`action_scale=0.15` 表示每步最多走半程的 15%）。比绝对位置好训，而且轨迹平滑得多 —— 如果这些策略以后要上真机，平滑性直接关系到腱和电机的寿命。想用绝对模式传 `--action-mode absolute`。

### 5. 域随机化（默认关闭）

```bash
python -m orca_rl.train --randomize-physics
```

每次 reset 随机方块质量（±30%）、摩擦（±30%）、关节阻尼（±30%）、执行器增益（±20%），并给关节角观测加约 0.3° 的噪声。

**先不要开。**先在确定性环境里证明任务能学会，再打开做 sim-to-real。一上来就开会让本来就难的探索问题雪上加霜。

## 超参数

默认值都写在 `train.py` 的 `parse_args()` 里。两个偏离 SB3 默认、但对这个任务很重要的：

- **`--ent-coef 0.0`**。直觉上 17 维连续动作需要熵来探索，但在这个任务上**熵项会失控** —— 详见文末的事故复盘。不要调高。`--max-log-std 0.0` 会额外硬 clamp σ ≤ 1 兜底。
- **`--log-std-init -0.5`**（SB3 默认 0，即 std=1）。在 `[-1,1]` 的动作空间里 std=1 意味着动作几乎总是撞到边界，每步都是最大增量，轨迹极度抖动。实测把它改成 -0.5 后 `clip_fraction` 从 0.57 降到 0.16，`approx_kl` 从 0.16 降到 0.03，全部回到健康区间。

还加了 `--target-kl 0.02`，让 SB3 在策略移动过远时提前结束 epoch 循环。

## 已知的坑

- **`SubprocVecEnv` 在 macOS 上必须有 `if __name__ == "__main__"` 保护** —— `train.py` 里已经有了。如果你自己写脚本调用，别忘了。调试时可以加 `--no-subproc` 退回单进程，报错栈会清楚很多。
- **评估时忘了加载 `vecnormalize.pkl`** 是最常见的「训练好好的、评估一塌糊涂」的原因。`evaluate.py` 和 `record.py` 会自动找同目录下的这个文件。
- **`checks.py` 里的 oracle 会瞬移方块**，那不是一个真实策略，只是奖励上限的参照。
- `record.py` 和 `evaluate.py` 用了 `env._cube_body_id` 这类私有属性 —— 上游没提供公开接口，先这么用。

## 事故复盘：v1 跑了 2000 万步，零进展

第一版（`success_bonus=5 / drop_penalty=10 / ent_coef=0.005 / goal_mode="axis"`）在 M4 上跑满 2000 万步，`task/solves_per_episode` 全程在 0.01–0.055 之间抖动，**没有任何趋势**。三个独立的错误叠在一起，每一个单独都足以让训练失败。

### 错误 1：熵项失控，σ 从 0.6 涨到 11

`train/std` 单调指数上升到 **11**。动作空间是 `[-1,1]`，std=11 意味着每个采样动作都饱和在边界 —— 训练时收集的全是 bang-bang 噪声，策略在自己均值附近的探索完全消失。

原因：高斯熵对 σ **没有上界**。正常情况下任务奖励会提供反向梯度把 σ 拉回来，但这个任务从没成功过，奖励梯度近乎为零，于是损失里唯一稳定的梯度就是熵项，PPO 老老实实把 σ 推向无穷。

`evaluate.py` 用 `deterministic=True`（只取均值 μ）所以看起来正常 —— **均值动作和实际训练行为已经完全脱节**。这是这个 bug 特别阴险的地方。

修复：`ent_coef` 默认改成 **0**，另加 `ClampLogStdCallback` 每轮硬 clamp `log_std <= 0`（σ ≤ 1）。

### 错误 2：掉落惩罚大于成功奖励，策略学会「夹住不动」

看视频才发现的：训练出来的策略把方块**卡死在手指和掌心之间，然后完全静止**，从第 4 秒到第 8 秒画面几乎不变。

原因很简单 —— `drop_penalty=10` 比 `success_bonus=5` 大一倍。手内操作必然伴随掉落风险，当「掉一次」的代价是「成功一次」的两倍、而成功还不确定时，**冻结是理性选择**。更糟的是夹死之后方块根本转不动，策略把自己锁死在了任务之外。

修复：`success_bonus` 5 → **10**，`drop_penalty` 10 → **5**。

### 错误 3：任务从第一步就是满难度

6 个轴向目标 + 至少偏离 60° 的约束 = **每次都是 90° 或 180° 的翻转**。这是 Dactyl 级难度，指望随机策略偶然完成一次来提供第一个学习信号，概率太低 —— 2000 万步实测 0 次。

修复：`goal_mode="curriculum"`（新默认）。目标是从当前朝向绕随机垂直轴转 θ 度，θ 从 **30° 起步**，按最近成功率自动调整（每 episode 解 ≥2 次就 +5°，≤0.5 次就 −5°），上限 180°。`task/goal_angle_deg` 会记进 TensorBoard，可以直接看课程进展。

### 修完之后

同一台容器（2 核，700 fps），**25 万步**：

| 指标 | v1 @ 2000 万步 | v2 @ 25 万步 |
|---|---|---|
| `solves_per_episode` | 0.01–0.055（无趋势） | **0.59** |
| `ep_rew_mean` | ~0.2 | **+4.9** |
| `train/std` | 0.6 → 11（失控） | 0.588（稳定，缓慢下降） |
| `drop_rate` | 0.04 | 0.14 |

**80 倍的步数差距，结果反过来。**顺带一提：修复后随机策略在 30° 课程下也能拿到 0.28 solves/episode，这正是「任务现在会发出学习信号」的直接证据 —— 之前是 0。

`drop_rate` 从 0.04 涨到 0.14 不是退步，是好事：策略终于愿意冒险动方块了，而不是夹死不动。

### 教训

三个 bug 里，**只有第一个能从曲线上看出来**（std 那条）。第二个只有看视频才能发现，第三个要靠算「这个任务到底有多难」。

`ep_rew_mean`、`explained_variance`、`approx_kl` 在 v1 里全部是健康的 —— explained_variance 甚至到了 0.95。**曲线全绿不代表在学正确的东西。**

## 复盘二：课程卡在下限，2000 万步没升过级

修完前面三个 bug 之后，run2 的结果是**真的学会了**：

| | run1 | run2 |
|---|---|---|
| solves / episode | 0.02 | **0.84**（最高 4） |
| ≥1 次的 episode | 2% | **52%** |
| mean return | −0.08 | **+6.23** |
| 首次成功耗时 | 从没有过 | **68 步**（1.4 秒） |
| 握住比例 | 90% | 97% |
| drop rate | 4% | 34% |

视频里的逐帧运动量也印证了行为的转变：

| | 运动量中位数 |
|---|---|
| run1（夹住不动） | 0.071 |
| run2（主动操作） | **2.051** |
| random | 4.928 |

**但 `task/goal_angle_deg` 在 2000 万步里一直在 26–27° 震荡，一次都没升上去。**下限是 25°，也就是说它被压在地板上。

原因是课程判据本身有两个错：

1. **用绝对成功次数** —— 一个 90 步就掉落的 episode 装不下 2 次成功，必然被判「太难」。掉落率一高，课程就被系统性地往下拽，**难度和 episode 长度被错误耦合**。
2. **每个 episode 都调整** —— solves 方差极大（近一半 episode 是 0），逐次反应等于随机游走：一次 0 降 5°，一次 2 升 5°，来回抵消。

修完之后用模拟数据验证判据的响应（200 个 episode）：

| 输入水平 | 课程终点 |
|---|---|
| 每 episode 解 2.0 次 | 30° → **80°** |
| run2 的水平（0.84 次） | 30° → **75°** |
| 从来解不出 | 30° → **25°**（正确地退到下限） |

而且它是自平衡的：难度上去之后成功率会掉，最终稳定在「速率≈1.0」的那个难度上。

### 教训

**自动课程本身也是一个需要调试的系统。**它有自己的失败模式，而且和策略的失败模式长得不一样 —— 策略明明在进步（0.02 → 0.84），课程却一动不动。如果只盯着 `solves_per_episode`，会以为一切正常；只有把课程难度也画出来，才能看到「策略在原地打转」这件事。

## 复盘三：45° 天花板 —— 一个目标能占掉整个 episode

run4 到 run6 一共跑了约 1.5 亿步，`task/goal_angle_deg` 从 42° 爬到 46° 就不动了，
`solves_per_episode` 一直在 0.5–0.6。曲线全部健康：`explained_variance` 0.90，
`approx_kl` 0.025，`drop_rate` 0.07，`std` 0.45 缓慢下降。**又是一次「全绿但不涨」。**

### 先做分解，不要直接调参

`diagnose.py` 把 45° 难度下的 run6 拆成两段：

```
REACH    goals that entered the cone: 55%      closest approach: median 13.9°（容差 15°）
CONVERT  conversion rate: 41%                  failed runs median length: 9 steps（需要 10）
         overshoot (cube still spinning): 59%  exit angular speed: median 1.50 rad/s
```

0.55 × 0.41 ≈ 0.22，和实测的每目标成功率对得上。两段都卡，而且卡的方式很具体：
**失败的目标中位数停在 14°，容差是 15°；失败的 hold 中位数是 9 步，门槛是 10 步。**
两个数字都差最后一点点 —— 这不是「学不会」，是「最后一段没有信号」。

再量一次每个目标花多少步：

```
解开的目标   : 中位数 48 步（0.48 秒）
没解开的目标 : 中位数 377 步 —— 一个 400 步的 episode 全耗在一个目标上
```

**一个 episode 平均只发生 1.9 次目标尝试。**而且没解开的那段里方块角速度均值 1.3 rad/s，
说明策略一直在动它，不是卡死 —— 是在慢慢地失败。

按目标的起始朝向 / 目标朝向 / 需要的旋转轴分桶统计，成功率在 28%–39% 之间，没有
明显的「某个轴根本转不动」。**所以不是embodiment的限制，是学习信号的问题。**

### 四个原因，四个修法

**1. 一个目标可以独占整个 episode。**新增 `goal_timeout_steps=150`：一个目标 150 步
没解开就判失败、换新目标（不给惩罚，机会成本已经够了）。拿 run6 的策略直接回放、
完全不重训：

| | 每 episode 目标数 | 每 episode 解开数 |
|---|---|---|
| 无超时（原来） | 1.87 | 0.87 |
| 超时 150 步 | 3.83 | **1.10** |

样本预算不变，学习信号翻倍。

**2. 势函数在终点处梯度消失。**shaping 用的是 `Δcos(θ)`，而 `d(cos θ)/dθ → 0`：

| 距目标 | 每度的 shaping | 相对 60° 处 |
|---|---|---|
| 60° | 0.01504 | 1.00 |
| 15° | 0.00437 | 0.29 |
| 5° | 0.00137 | **0.09** |

**越接近目标，奖励梯度越小 —— 而这个任务全部的难度都在最后 15°。**
新增 `shaping_mode="angle"`（默认）：势函数改成 `-θ/π`，每一度处处等价。

**3. 没有任何项为「刹车」付钱。**59% 的失败 hold 是方块带着 1.5 rad/s 冲出容差锥。
`spin_penalty=0.05` 现在默认打开：在锥内按角速度罚。

**这里踩了一个新坑**：我一开始把罚的范围放宽到 `spin_band=2.0`（即 30°），
想让策略在接近时就开始减速。结果 `checks.py` 立刻报警 —— 「什么都不做」的回报从
+0.01 掉到 **−2.59**。原因是课程在 30° 时目标就在 22.5–30° 处，**整个目标范围都落在
罚区里**，方块在掌心自然沉降的抖动都在被罚。而对「一直在被罚」的最优应对是把方块
夹死不动 —— 正是复盘一错误 2 的翻版。默认改回 `spin_band=1.0`，回到 +0.01。

**`checks.py` 在训练开始前 30 秒内抓到了这个。**这就是为什么每次改奖励都要先跑它。

**4. `align_bonus` 可以被无限刷。**原来的注释说「每个目标最多付 `hold_steps × align_bonus`」——
是错的。`hold_counter` 每次离开锥都清零，所以在锥边缘来回振荡可以一直拿钱，
就是原版 stalling 漏洞换个马甲。现在每个目标有一个 `hold_steps` 次的预算，用完为止。
`checks.py` 里加了 `hover on the cone edge` 这条脚本策略专门验证：返回 −10.46、0 次成功。

### 课程判据（第二次重写）

复盘二把判据从「绝对次数」改成「按速率」，但门槛留在 **每 episode 解 1.0 次**。
实测 run6 在 45° 处只能到 0.6，**这个门槛物理上够不到**，所以难度在 45° 稳定了 1.5 亿步。
而且它仍然和 episode 长度耦合。

现在换成**按目标尝试的成功率**（`curriculum_metric="goal_success"`）：每个目标尝试
被 `goal_timeout_steps` 封顶，分母是一个固定的「机会单位」，和掉落率、episode 长度
都无关。成功率 ≥0.55 升 5°，≤0.25 降 5°，窗口 40 次尝试 —— 这就是标准的
「让难度跟着学生的成功率走」。窗口从 20 个 episode（约 8000 步/env）缩到 40 次目标
尝试（约 2000 步/env），课程的反应速度快了约 4 倍。

> 注意：新判据下 45° 对应的成功率是 0.34，低于 0.55，所以续训时课程会**主动降到
> 30° 左右**。这不是退步，是重新标定 —— 旧判据把策略留在了一个它只能做对三分之一的
> 难度上。

### 另外两个顺手修掉的

- **`--gamma` / `--gae-lambda` 在 `--resume` 时被静默忽略**：`custom_objects` 里没列它们。
  run3–run6 全部是在 γ=0.99 下跑的，不管命令行写了什么。已补上。
- **γ 0.99 在 100 Hz 控制率下只有 1 秒视野**，而一次目标尝试最长 1.5 秒，
  成功奖励在策略需要做决定的时刻已经被折掉一半。默认改成 **0.995**（2 秒）。

### 新的监控指标

| 指标 | 含义 |
|---|---|
| `task/goals_per_episode` | 每 episode 发生几次目标尝试。应该在 2.5–3.5；掉到 2 以下说明超时没生效 |
| `task/goal_success_rate` | **现在真正的进度指标。**课程会把它稳定在 0.25–0.55 之间 |
| `task/goal_angle_deg` | 难度。`goal_success_rate` 贴着 0.55 时它才会涨 |

看这两个的组合：`goal_success_rate` 稳定在带内而 `goal_angle_deg` 在涨 = 正在进步；
两个都不动 = 又到了一个天花板，回去跑 `diagnose.py` 再分解一次。

## 复盘四：run8 没有变好，以及三个结构性问题

### 先更正：run8 是退步

run8 从 run6 热启动、带着复盘三的全部改动跑了约 4000 万步。训练曲线上 `solves_per_episode`
从 0.62 涨到 ~1.0，看起来是进步。**在修好的环境里用固定难度重新评估（60 episode，确定性策略）：**

| | 30° 目标成功率 | 45° 目标成功率 | 掉落率（30°） |
|---|---|---|---|
| run6 | **39%** | **29%** | 12% |
| run8 @ 2.01 亿步 | 30% | 15% | 3% |

run8 学会了更少掉方块，但转得更差。训练曲线上的涨幅来自「每 episode 目标尝试变多」
（`goal_timeout`）和下面第 1 个 bug 的白送成功，**不是策略变强**。课程也一路退到了 25° 下限。
热启动 + 同时改奖励、γ、课程，没法拆开是哪一项造成的退步 —— 所以下一轮要从头跑、做对照。

### 1. reset 之后方块自己倒进容差锥（白送 +10）

方块在 0.19 m 生成，落到掌心 ~0.174 m 时**倾倒约 21°**，35–50 步才静止。目标却是在下落
**之前**按原始朝向抽的（距离 22.5–30°）。结果：**不动的策略在 30° 难度下 26% 的 episode
在第 13 步左右「成功」一次。**越接近课程下限越严重 —— 而 run8 正好一直停在下限附近。

原来的 `checks.py` 只跑了 seed 0 的一个 episode，恰好没中，所以 run1–run8 都没发现。

修复：`reset_settle_steps=60`，reset 时先让方块落稳（手保持初始目标，不像父类的
`settle_steps` 那样每步把目标改成当前角度、让手软塌），**然后**再抽目标；并沿用落稳时的
伺服目标作为第一步的起点（否则第一步伺服目标一跳，手指一松，方块滚 10°、滑 18 mm）。
修完后零策略 300 个 episode 0 次成功；`checks.py` 新增这条断言，并确认它在旧 reset 下会报警。

### 2. 观测里没有伺服目标 —— 策略看不见自己在「用多大力」

`action_mode="relative"` 下动作是**在上一个目标上的增量**，所以 `_prev_target` 是控制器的
积分器状态 —— 但它不在观测里。它和 `qpos` 的差在手指压着方块时最大，而
`kp * (target - qpos)` 就是握力。

实测 run6/run8 **77% 的时间伺服目标顶在 ctrlrange 的边界上**，目标与实际关节角平均差
0.17 个半程。策略在 bang-bang：它看不到自己的目标在哪，只能把积分器推到头。这和复盘三里
「到了锥里停不住」（59% overshoot）是同一件事的两面 —— 靠撞限位控制不了精细动作。

修复：`obs_include_target=True`，观测末尾加上归一化到 `[-1,1]` 的伺服目标，**54 → 71 维**。
旧 checkpoint（54 维）在 evaluate / diagnose / record / `--resume` 中自动按旧格式加载。

### 3. `--n-epochs 10` 从来没生效

run8 的 628 次更新**全部**在第一个 epoch 内就被 `target_kl` 截停，每个样本只用了一次或更少。
用同一份 rollout、同一份权重和 Adam 状态回放：

| batch | lr | 实际完成 epoch | 梯度步数 |
|---|---|---|---|
| 256 | 3e-4（旧默认） | **1** | 16 |
| 1024 | 1.5e-4（新默认） | **4** | 16 |
| 2048 | 3e-4 | 4 | 8 |

同样 16 步梯度，新默认把数据过 4 遍、每步用 4 倍样本。TensorBoard 新增 `train/epochs_used`，
长期贴着 1 就说明又被截停了。

### 其他小问题

- `--resume` 时 `--timesteps` 是**追加**的步数（SB3 `reset_num_timesteps=False`）。
  run8 我按「总步数 1.68 亿」传了 168M，结果它会跑到 3.28 亿。help 里已写明。
- `VecNormalize` 的 reward 归一化有自己的 `gamma`（默认 0.99），现在和 PPO 的 `--gamma` 同步。

### 下一轮：从头跑，两臂对照

观测维度变了，必须从头训。第二臂关掉复盘三加的两个奖励项，用来判断 run8 的退步是不是它们造成的：

## 复盘五：run9 的结果，以及复盘三的诊断本身是错的

### run9：用 1/5 的步数达到 run6 的水平，天花板没动

全部采用固定难度评估，100 个 episode、`--seed 0`，都在修好的环境里测：

| | 训练步数 | 30° | 45° | 60° | 掉落（45°） |
|---|---|---|---|---|---|
| run6 | 1.6 亿 | 38% | 31% | 17% | 10% |
| **run9** | **3000 万** | **44%** | **32%** | **20%** | 4% |

在 45° 下每 500 万步扫一次 checkpoint：29% / 20% / 28% / 29% / 35% / 32%。**500 万步以后基本就不涨了。**
复盘四的结构性修复（settle、伺服目标进观测、PPO epoch）换来的是**样本效率**和更低的掉落率，没有抬高能力上限。

### 复盘三的「HOLD 受限、59% overshoot」是 diagnose 的计数 bug

成功发生的那一步，env 已经把目标换成下一个了，所以 `info["aligned"]` 是按**新目标**算的，结果为 False。
`diagnose.py` 先把这一步当成「出锥」，把刚守住的 9 步记成一次失败，再按当时的角速度（>1 rad/s）
归类成 overshoot，然后才把这次成功记上。**每次成功都被重复算成一个假的「9 步 overshoot 失败」。**
所以 run6、run8、run9 的「失败 hold 中位数」都正好是 9 步。

修正之后（45°）：

| | run6 | run9 |
|---|---|---|
| 进锥率（REACH） | 27% | 33% |
| 转化率（CONVERT） | ~~45%~~ **83%** | ~~40%~~ **68%** |
| 真实失败的 hold，中位数长度 | 2 步 | 3 步 |

**瓶颈一直是 REACH**：大约 70% 的目标从来没进过 15° 的锥，一般停在离目标 ~20° 的地方。
`spin_penalty` 和 `align_bonus` 是为了解决一个并不存在的问题加的。run10（这两项都关）在 950 万步时，
30° 已经到 45%，而 run9 同步数时是 34%。这和上面的结论一致，但需要等两组都跑完再下结论。

时间不是瓶颈：同样 800 步里，把每个目标的超时从 150 步加到 300 步再到不限，进锥率 30% → 39% → 54%，
但**总解开数** 96 → 75 → 56。多出来的时间都耗在磨不动的目标上了，150 步已经是吞吐最高的设置。

### 教训

诊断工具本身也要验证。这个 bug 让一次错误的诊断看起来非常具体、可信（「差最后 1 步」「1.5 rad/s 冲出去」），
然后顺理成章地引出一个错误的修复。**「失败都卡在门槛前一步」这种过于整齐的数字，本身就是一个警告信号。**

## 复盘六：run10 —— 刹车项买到了转化率，但赔掉了 REACH

run10 = run9 去掉 `spin_penalty` 和 `align_bonus`。完整记录见 `results/2026-09-23-run10.md`。

|---|---|---|---|

## 复盘十：旋转向量 —— 第一个真正的突破

完整记录见 `results/2026-09-25-run18-19.md`。

观测里加入一个 3 维的旋转向量（`--obs-rotvec`）：方向是把红面转到目标该绕的轴，长度是还差的角度。只改观测，不改奖励。

| 目标成功率（评估 seed 0） | 30° | 45° | 60° |
|---|---|---|---|
| 基线 run10 / run12 | 49% / 53% | 39% / 37% | 28% / 25% |
| **旋转向量 run18 / run19** | **77% / 66%** | **65% / 55%** | **54% / 41%** |

两个 seed、三个难度全部大幅领先。换评估 seed 也能复现；90° 下是 37% / 25%，基线只有 7% / 6%。

之前 run10–run17 的 8 组实验，一直在改奖励、掉落处理、动作尺度，没有一个能突破 45° 下 35–40% 的平台。
这个平台其实是**表示能力**的问题：策略看得到红面朝向和目标朝向，但要从这两个向量里自己算出「绕哪个轴转、还差多少」，对这个 MLP 太难了。

另外，训练中的 `goal_success_rate` 被课程固定在 0.4 附近，所以它根本反映不出进展。
**真正的进度指标是课程难度 `goal_angle_deg`**：run18 最后到了 81°，基线只有 42°。

新的弱点是掉落：60° 下掉落 16–19%，90° 下 31–41%。
